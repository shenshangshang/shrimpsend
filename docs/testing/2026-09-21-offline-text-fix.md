# 手机发文件成功、发文本失败：修复与验证

## 原因

手机 16:29 的应用日志显示，文本发送和多次重试均请求 `http://localhost:9000/api/messages/device-send`，返回连接拒绝。当时手机的 USB API / 信令转发已不存在，局域网 HTTP 文件接收端仍正常。

Flutter 文本选路遗留了账号条件：只有“已登录且对端不属于当前设备列表”才走 LAN；游客文本始终请求服务器。文件已使用按设备可达性选择通道的流程，造成“文件成功、文本失败”。上一轮文本实测时服务可达，没有覆盖免登录、服务不可达时从实际输入框发送的组合。

## 修复

- 首次发送和失败重试共用 `TextDelivery`：不以账号判断通道，优先使用发现到的及已记住的 LAN 地址；无法直达时再使用设备凭证请求服务器。
- 局域网请求设置 3 秒超时，服务端路径设置 12 秒超时；成功直达时不请求服务器，也不要求登录。
- LAN 请求携带收件设备 ID，错误地址指向另一台设备时由接收端拒绝，不串发消息。
- 新文本携带稳定 `textId`，LAN、服务端回退、重试及历史使用同一接收身份，避免重复气泡和重复记录。旧消息的身份规则保持兼容。
- 重试仍使用原消息标识，并阻止正在发送的同一气泡重复触发。

## 验证

在 Xiaomi Android 16 真机与实际 Mac 客户端之间，保持手机 API / 信令不可达，从手机输入框和失败气泡实际操作：

| 场景 | 结果 |
|---|---|
| 免登录发送中文、英文和表情 | LAN 发送成功，Mac 接收内容一致 |
| 多行文本 | LAN 发送成功，换行保留 |
| 长文本 | LAN 发送成功，Mac 内容与去除首尾空白后的输入一致 |
| 已持久化的失败文本点击重试 | LAN 发送成功，原消息状态更新为 sent |
| 对其中一条消息再投递两次 | Mac 数据库仍只有一条对应记录 |

本次 4 条消息在接收端逐条比对文本，结果完全一致；重复请求后仍是 4 条。测试中设备始终未连接信令。证据：`.local/android-offline-text-verified.json`、`.local/android-offline-text-real.log`。

23 项相关回归测试通过：14 项覆盖真实 HTTP 服务的文本接收与目标校验、离线 LAN 成功、旧地址回退、超时、消息身份及既有文件直写与续传；另外 9 项覆盖会话历史、消息气泡身份和线程键。静态检查无 error / warning，保留少量 info 提示。真机测试入口：`app/integration_test/offline_text_delivery_test.dart`。

第一次长文本测试的断言使用了带末尾空格的原始输入，而产品会按既有行为去掉首尾空白，导致等待断言未结束；调整断言后重新运行全部真机步骤通过。该问题不属于文本丢失。

安装使用现有 `dev.ultrasend.app.local` 的同签名覆盖安装，未卸载或清除数据；设备身份保持不变。测试结束后恢复普通 App 和 API / 信令转发。修复后的同 LAN 文本传输本身不依赖这些转发。
